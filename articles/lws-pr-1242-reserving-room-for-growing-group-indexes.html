LWS PR #1242: reserving room for growing group indexes

This merged change budgets generated External-role names for a larger group index while preserving older objects with an admission warning.

Before and after

Before

An External role's ignored spec.replicas could leave too little room for a generated group index. After a scaler grew past ten groups, a generated Pod label could exceed Kubernetes' 63-character limit.

After

New External roles reserve eight digits by default. Existing External roles keep their accepted update budget and get a warning when their name cannot reach the new limit. The PR was merged.

Why this began

I developed the fix from issue #1241, which showed the generated pod label could exceed Kubernetes' 63-character limit.

This is a field note about one contribution trail: what I saw in the issue or pull request, how the change was shaped by review, what the public record says was tested, and what is still uncertain. The linked repository remains the authority for the current upstream state.

The spark

Name length becomes a scaling limit when the index is part of a label, and admission has to account for future growth.

The practical value is in making this piece of project work reviewable. A small change has to fit the surrounding conventions, give maintainers enough context, and make its limits clear. The thread and diff are the evidence for that process; this post keeps the proposed scope and recorded outcome distinct.

A small index exposed a boundary bug

The problem is a name budget, not that ten is a special number. The generated role/group name feeds a Pod label with a hard 63-character limit. An External role's spec.replicas is ignored by the scaler, so validation that reserves one digit can accept a name that later cannot be instantiated.

The change reserves eight index digits for new External roles, including transitions into External mode and External sub-roles. Static and hash-identity roles retain their existing rules.

Why review reduced the configuration surface

An early version added a manager setting for the reserved digit count. Review raised the cost of turning a one-off compatibility rule into a new configuration API. The final change removes that option and reuses the existing hash-prefix constant.

Review also preserved updates for already accepted objects. Existing External names keep their old budget, with an admission warning describing how many groups they can support. This avoids making stored objects impossible to edit because a new default is stricter.

Tradeoff and verification boundary

The PR states the cost: with the default group identity, the set name and new External role name can be at most 31 characters combined. There is no opt-out. The PR reports webhook unit and integration tests passing on Linux, but says the warning was tested directly through validation, not through a real API server.

What this PR does / why we need it

validateGeneratedNames reserves room in the name budget for the largest group index, using validationReplicasForRole. For an External role that is the ignored spec.replicas (a single digit when omitted), and each External sub-role counts as one replica. The scaler's spec.replicas has no upper bound, so once an autoscaler grows the role past ten groups, the worker StatefulSet &lt;lws&gt;-&lt;groupIndex&gt; can give its Pods a controller-revision-hash label longer than 63 characters, and the new group's Pods cannot be created (the failure fixed for known replica counts in #972).

This PR makes a role or sub-role that becomes External reserve room for a group index of 8 digits by default, the same room groupIdentity: Hash reserves for its group key (webhooks.HashDNSPrefixLength, exported for this):

  • New External roles, roles switching from Static to External, newly added External sub-roles, and External roles leaving groupIdentity: Hash get the new budget. The error message says why.
  • Roles and sub-roles that were already External with an indexed groupIdentity keep their earlier budget on updates, so stored DisaggregatedSets accepted before this change stay updatable. When their names cannot hold an 8-digit group index, each update returns an admission warning with the number of groups the names allow.
  • Static roles and groupIdentity: Hash roles are unchanged (Hash names contain no group index).
  • The role-scaler page documents the limit and what happens past the budget.

Which issue(s) this PR fixes

Fixes #1241

Special notes for your reviewer

  • Trade-off: with the default groupIdentity, the DisaggregatedSet name plus an External role's name can be at most 31 characters combined, down from 38. That is the limit a Hash role with size above 1 already has. A role at this limit can reach 100 million groups; past that, new groups' Pods would hit the same label error, which the docs call out. Replicas stay uncapped.
  • Recreating a DisaggregatedSet with a longer name is rejected, since admission treats it as new. There is no setting to change this, so such names must be shortened.
  • No configuration option: an earlier version of this PR added a manager option for the reserved digits. It was removed in review, so that this limit adds no v1 API surface, matching the fixed limit of groupIdentity: Hash.
  • The legacy exemption follows the same idea as unchangedRoleTemplate: it compares the role's External leaves with the stored object's, matching sub-roles by name.
  • Unit tests cover the limit edges for ordinary and partitioned roles, the reproduction from the issue, unchanged Static and Hash budgets, the update cases including External roles leaving Hash, an over-limit Hash role, static sub-role counts above the reserved digits, and when the warning is returned.
  • The docs name LWS v1.1 as the release that introduces this limit, based on the open 1.1.0 milestone and the existing release-1.0 branch. Change that if this is cherry-picked to a 1.0.x release.

Does this PR introduce a user-facing change?

DisaggregatedSet: admission now reserves room in generated names for the group index of a new External role or sub-role, so an autoscaler growing the role cannot produce Pod labels longer than 63 characters unless it passes the reserved size. This is 8 digits (100 million groups): with the default groupIdentity, the DisaggregatedSet name and a new External role's name can be at most 31 characters combined. Roles that were already External keep their earlier limit on updates, with an admission warning when their names cannot hold 8 digits.

What I put in the issue description

The text below is my original public description, preserved so the scope and evidence are inspectable. It is useful context for reading later commits and review comments; it is not a substitute for the final merged code.

What happened:

validateGeneratedNames reserves room in the name budget for the largest group index, taking the replica count from validationReplicasForRole. For a role with scaling.mode: External, that returns spec.replicas, which External roles ignore. When it is omitted, the webhook budgets a single digit for the group index. For a partitioned role, each External sub-role counts as one replica.

The real replica count comes from the role's DisaggregatedSetRoleScaler, which is limited only to Minimum=0 and is not validated by the DisaggregatedSet webhook. When an autoscaler scales the role past 10 groups, the group index gains a digit. The worker StatefulSet &lt;lws&gt;-&lt;groupIndex&gt; then gives its Pods a controller-revision-hash label of &lt;lws&gt;-&lt;groupIndex&gt;-&lt;hash&gt; longer than 63 characters, so the new group's Pods cannot be created. This is the failure fixed for known replica counts in #972.

This is the same root cause as #1229: admission sizes an External role from the ignored spec.replicas instead of its scaler's target.

What you expected to happen:

Admission should not accept generated names that a valid scaler target can push over the limit. External roles and sub-roles have no upper bound at admission, so the budget for their group index should not depend on spec.replicas.

How to reproduce it (as minimally and precisely as possible):

A 31-character DisaggregatedSet name and the 7-character role prefill give a 50-character LWS name. Admission accepts it, because with one index digit the longest derived name is exactly 63 characters:

apiVersion: disaggregatedset.x-k8s.io/v1
kind: DisaggregatedSet
metadata:
  name: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
  namespace: default
spec:
  roles:
    - name: prefill
      scaling:
        mode: External
      spec:
        leaderWorkerTemplate:
          size: 2
          workerTemplate:
            spec:
              containers:
                - name: main
                  image: registry.k8s.io/pause:3.10

Then scale the generated scaler to 11 groups:

kubectl scale disaggregatedsetrolescaler aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa-prefill --replicas=11

Group 10's worker StatefulSet is &lt;50-char LWS name&gt;-10, and its Pods' controller-revision-hash label is 64 characters, so they cannot be created. Groups 0 to 9 are unaffected, so the failure appears only once the autoscaler grows the role.

Anything else we need to know?:

Possible fixes, from simplest:

  1. Budget External roles and sub-roles for the largest group index any scaler target can produce (10 digits for int32). This is consistent with #1230, which validates External budgets as if any size were possible, but it shortens the combined name limit for External roles by 9 characters.
  2. Budget a documented maximum and cap the scaler's spec.replicas at that value in its CRD.

To avoid rejecting existing DisaggregatedSets on unrelated updates, the stricter check could apply only when a role is created or becomes External, as unchangedRoleTemplate already does for other legacy templates.

I would like to work on this.
