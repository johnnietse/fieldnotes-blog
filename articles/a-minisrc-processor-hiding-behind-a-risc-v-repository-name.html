MiniSRC Processor

ELEC 374 — Queen's University 32-bit multi-cycle processor implementing a MIPS-inspired instruction set architecture.

---

Architecture Overview

The MiniSRC executes instructions in a 5-cycle pipeline controlled by a rotating one-hot FSM:

┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│  FETCH  │───>│  DECODE │───>│ EXECUTE │───>│ MEMORY  │───>│WRITEBACK│
│ Cycle 1 │    │ Cycle 2 │    │ Cycle 3 │    │ Cycle 4 │    │ Cycle 5 │
│ IR←Mem  │    │ RF Read │    │ ALU Op  │    │ Ld/St   │    │ RF Write│
│ PC+=4   │    │ Decode  │    │ Branch  │    │ Port IO │    │         │
└─────────┘    └─────────┘    └─────────┘    └─────────┘    └─────────┘

Key Specifications

FeatureDetail
Word size32 bits
Registers16 × 32-bit (R0 = 0)
Address space32-bit, byte-addressed
Memory1024 × 32-bit block RAM
ALUCLA adder, Booth multiplier, non-restoring divider, barrel shifter, rotator
I/O18-bit switch input, 32-bit seven-segment output
TargetAltera DE-series (Cyclone V 5CEBA4F23C7)

Building & Running

FPGA Synthesis

# Open in Quartus Prime, compile, and program DE2 board
quartus_sh --flow compile mini_src_processor
quartus_pgm -c 1 -m JTAG output_files/mini_src_processor.sof

Assembling Programs

cd firmware_tools/custom_assembler
python srcasm.py ../test_programs/phase4.s -o ../test_programs/program.hex

Running Simulations

cd verification/sim_scripts

# Full processor testbench
vsim -do run_processor.do

# Individual unit tests
vsim -do run_alu_tests.do
vsim -do run_regfile_tests.do
vsim -do run_memory_tests.do

What I learned and what I would carry forward

The first commit calls the change a complete restructure and rewrite. The most valuable next cleanup is making the repo title and documentation agree about which architecture it implements.

The lasting lesson is specific to this record: The spark is building up a processor from its instruction set and cycle-level behavior rather than treating the CPU as a black box. The next time I meet a similar problem, I would start by writing down the observable behavior, the constraints that define a correct result, and the smallest check that would distinguish a real fix from a plausible-looking change. For a design project, that means making requirements and drawings traceable. For a code contribution, it means connecting the issue, patch, review response, commit, and test output so a maintainer can follow the reasoning without reconstructing it from memory.

This is also why I keep the limits in the story. A portfolio entry is more credible when it identifies what was done, what the evidence confirms, and which environment or outcome still needs a fresh check. The public history is useful precisely because it lets a reader inspect those boundaries.
