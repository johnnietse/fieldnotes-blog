What this PR does / why we need it

Available on a DisaggregatedSet is a completion signal: it goes False on every rollout and scale-up, even when no role drops below what maxUnavailable permits. Clients that need to know whether enough is serving (health checks, alerts, parent controllers such as KServe) currently have to reimplement LWS's availability rules.

This publishes the rollout planner's existing view of availability, without changing the planner or the meaning of Available/Progressing:

  • RoleStatus.minAvailableReplicas / SubRoleStatus.minAvailableReplicas: the planner's availabilityFloor for each current role, max(0, desired - maxUnavailable) per slice, with the budget resolved against the latest target exactly as for rollout steps, totalled across slices. A partitioned parent reports the sum of its children. Unset while any contributing target is unknown, like desiredReplicas.
  • RoleStatus.availableReplicas / SubRoleStatus.availableReplicas: Ready groups that can serve. As in the planner's usable capacity, a group counts only in a revision of a slice where every role that revision requires has a Ready group (required = max(Spec, initial-replicas) &gt; 0; on an old revision, sub-roles use their issued or frozen counts). The current revision requires every role and sub-role with a positive resolved target, even while its workload is missing, because sub-role changes update its workloads in place. Old workloads are judged by the layout recorded on them, whatever the current spec says, and old revisions of removed roles take part in that check. A role's count never exceeds its readyReplicas.
  • MinimumReplicasAvailable condition: True while every parent and child has availableReplicas &gt;= minAvailableReplicas; False with the roles below their floor in the message (e.g. decode (2/3)), plus any unknown floors; otherwise Unknown while a floor is unknown. Independent of the Available/Progressing pair.

This takes both shapes proposed in the issue, and answers its open question about cross-role capacity: a role above its floor does not help if a peer in the same revision has no Ready group, because its groups are not counted as available.

Also updates KEP-766 (new "Reporting availability" section and history entry), the API reference, and the rollout-strategy and role-scaler concept docs.

Fixes #1191

Special notes for your reviewer

  • Scale-ups follow the new target. The floor uses the latest desired count, matching a Deployment's MinimumReplicasAvailable (available &gt;= desired - maxUnavailable) and the planner. A scale-up larger than maxUnavailable (e.g. 4 to 6 with maxUnavailable: 1) therefore reports False until enough new groups are Ready; a percentage budget scales with the target. Treating a scale-up as satisfied would need the pre-scale-up count, which a stateless controller does not keep. This is documented in the KEP and the rollout-strategy page. Happy to revisit if you'd prefer a different rule.
  • Deferred External roles: the planner may protect more than the published floor while its effective desired count exceeds the latest scaler target. The field doc says so.
  • Condition messages list the first ten roles of each kind plus how many more, so a long list cannot make the API reject the status update. The same cap applies to the existing unresolved-scaler message, which had the same problem.
  • collectRoleStatuses now lists the set's LeaderWorkerSets once and groups by role, so removed roles can take part in the revision check.
  • Unit tests cover floor resolution (per-slice percentages, overrides, unknown targets), same-revision and per-slice usable capacity (including frozen baselines, removed roles, missing workloads and recorded partitioned layouts), the condition states and message cap, and end-to-end updateStatus cases for a rollout and a scale-up within maxUnavailable. The updated e2e assertion in test/e2e/disaggregatedset/subroles_test.go was not run locally.

Does this PR introduce a user-facing change?

DisaggregatedSet: each role and sub-role status now reports `minAvailableReplicas` (desired minus maxUnavailable, totalled across slices) and `availableReplicas` (Ready replicas whose revision has every required role Ready), and a new `MinimumReplicasAvailable` condition reports whether every role meets its floor. Unlike `Available`, it stays True during rollouts and scale-ups that remain within each role's maxUnavailable budget.

My public comments and review activity

November 1, 2026Issue discussion

What would you like to be added:

A status signal saying whether each role is serving at least its allowed minimum, separate from whether its rollout or scaling has finished.

Today Available means every role has reached its desired replica count with all replicas ready and updated. That is a completion signal. There is no signal for "enough is serving", which is what Available means on a Deployment (ready ≥ desired − maxUnavailable).

Possible shapes:

  1. Per role: add the role's availability floor (and optionally availableReplicas) to RoleStatus.
  2. Whole set: a new condition such as MinimumReplicasAvailable, True while every required role is at or above its floor. A new condition avoids changing the meaning of Available.

Why is this needed:

Available goes False on every routine change, even when the service never drops below what the user allowed:

  • Scale-up: an autoscaler moves a role from 4 to 6. Available is False until the 2 new replicas are Ready, which can take minutes for model servers, while the original 4 keep serving.
  • Rollout: a role with 4 replicas and maxUnavailable: 1 is updated. At least 3 serve throughout, but Available is False until the last replacement is Ready.

So health checks, alerts and parent controllers see an outage during normal operations, or must re-implement LWS's availability rules themselves.

The controller already computes this: since #1181, the rollout planner keeps a per-role availability floor (availabilityFloor: max(desired, unreplaced) − maxUnavailable) and tracks usable capacity across required roles. This asks to publish that view, not to define new rules.

Open question: a request needs every required role, so a role above its floor is not enough if a peer is at zero. The set-level signal should probably use the planner's cross-role usable capacity (see #1178, #1180).

We hit this in KServe, which runs prefill/decode services on DisaggregatedSets (kserve/kserve#6383). It cannot use Available for readiness, because every autoscaler scale-up would mark the service not ready, so it recomputes availability itself.

Related: #1192 proposes publishing each role's target (desiredReplicas). This request is independent, but the two would sit together in RoleStatus.

November 1, 2026ahg-g · pkg/controllers/disaggregatedset/status.go

Fall back to capacity.observeWorkload in observeServingLayout whenever lws is on the current revision or membership == nil.

func (m *LeaderWorkerSetManager) observeServingLayout(ctx context.Context, capacity servingCapacity, lws *leaderworkersetv1.LeaderWorkerSet, role, revision string) error {
	membership, _ := subRoleCounts(lws, subRoleReplicasAnnotation)
	if lws.Labels[disaggregatedsetv1.RevisionLabelKey] == revision || membership == nil {
		capacity.observeWorkload(lws, role)
		return nil
	}
	initial, _ := subRoleCounts(lws, disaggregatedsetv1.InitialSubRoleReplicasAnnotationKey)

Why: Because ComputeRevision zeroes role.SubRoles, dropping subRoles from a role updates the existing current-revision LWS in place: requireTargets requires the parent key role while observeServingLayout records Ready counts only under child keys role/&lt;child&gt;, leaving ready[role] == 0. In addition, when membership == nil and initial != nil (for example after Create writes only initial-subrole-replicas, or when subrole-replicas is invalid), requireSubRoles requires every initial child while membership[name] rejects every group on the nil map — in both cases serves() returns false and zeroes availableReplicas across every role in the slice.

Why it's safe: collectRoleStatuses only calls observeServingLayout for unpartitioned or removed roles, where requireTargets already requires parent keys on the current revision while old revisions keep enforcing their recorded child layout when membership != nil.

What I learned and what I would carry forward

The discussion led to PR #1233, where review sharpened behavior for missing workloads, old recorded layouts, and False versus Unknown. The issue is closed and the corresponding PR merged.

The lasting lesson is specific to this record: A rollout can be incomplete while the service is still available enough to serve, so one condition cannot answer both questions. The next time I meet a similar problem, I would start by writing down the observable behavior, the constraints that define a correct result, and the smallest check that would distinguish a real fix from a plausible-looking change.
