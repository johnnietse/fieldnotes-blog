What I learned and what I would carry forward

Review surfaced unrelated files touched by a Prettier pass because main itself needed formatting. I documented the branch history, then the team split formatting and feature changes. This PR is closed without a merge recorded; the later clean sequence is #25–28.

The lasting lesson is specific to this record: A route change can be the last small step between a component that exists and a workflow a user can reach. The next time I meet a similar problem, I would start by writing down the observable behavior, the constraints that define a correct result, and the smallest check that would distinguish a real fix from a plausible-looking change. For a design project, that means making requirements and drawings traceable. For a code contribution, it means connecting the issue, patch, review response, commit, and test output so a maintainer can follow the reasoning without reconstructing it from memory.

This is also why I keep the limits in the story. A portfolio entry is more credible when it identifies what was done, what the evidence confirms, and which environment or outcome still needs a fresh check. The public history is useful precisely because it lets a reader inspect those boundaries.
