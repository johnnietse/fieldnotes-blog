cuda-GPU-programming

Overview

This repository contains my work for Machine Problem 1 (MP1) and Machine Problem 2 (MP2) from the Digital Systems Engineering course at Queen's University. These assignments focus on GPU programming using CUDA to explore matrix multiplication and device capabilities on NVIDIA GPUs.

Machine Problem Details

MP1: Device Query and Basic Matrix Multiplication

  • Part 1: Device query to identify GPU capabilities (clock rate, memory, threads, etc.)
  • Part 2: Implementation of a basic GPU matrix multiplication kernel with performance analysis
  • Data transfer time measurements (host-to-device and device-to-host)
  • CPU vs GPU performance comparison
  • Thread/block configuration experiments

MP2: Optimized Tiled Matrix Multiplication

  • Part 1: Implementation of a shared memory (tiled) matrix multiplication kernel
  • Performance analysis with different tile sizes (2, 4, 8, 16, 32)
  • Comparison with MP1 baseline implementation
  • Part 2 (Bonus): Revised tiled kernel with boundary checks for non-square matrices

GPU Environment

All work was completed on one of the following GPU machines:

  • 24 remote access machines with NVIDIA T600

All machines run:

  • Visual Studio 2022
  • CUDA 12.2

A small, real code sample

Excerpt from MP1_Part1.cu (line 2). Kept short enough to discuss; open the file for context.

#include "device_launch_parameters.h"
#include "cuda_runtime.h"

int main()
{
    int deviceCount;
    cudaError_t error = cudaGetDeviceCount(&deviceCount);
	
	//if it is not a valid CUDA device then return 1 and exit the program
    if (error != cudaSuccess) {
        printf("Cuda Error: %s\n", cudaGetErrorString(error));
        return 1;
    }
	
	//sometimes there can be more than one device, so this "for loop" is for looping through all available devices and printing out their properties
    printf("Number of available devices %d \n", deviceCount);
    for (int i = 0; i < deviceCount; i++) {
        cudaDeviceProp gpuProperties;
        cudaGetDeviceProperties(&gpuProperties, i);
        printf("-----------------------------------------------------------------------------------\n");
        DisplayDeviceSpecificationsfn(gpuProperties);
    }
}



//function to display and print off all the GPU device properties

void DisplayDeviceSpecificationsfn(cudaDeviceProp gpuProperties) {
    printf("CUDA Device Name and Type: %s \n", gpuProperties.name);
    printf("Clock Rate: %d\n", gpuProperties.clockRate);
    printf("Number of Streaming Multiprocessors (SM's): %d\n", gpuProperties.multiProcessorCount);


    //initialize all the variables for calculating the number of CUDA cores
    int majorVersion = gpuProperties.major;
    int mPCount = gpuProperties.multiProcessorCount;
    int totalCoresCount = 0;


    if (majorVersion == 2) {
        totalCoresCount = 32 * mPCount;

What I learned and what I would carry forward

These assignments are a useful start in parallel programming: performance depends on both the algorithm and how work is divided across the device.

The lasting lesson is specific to this record: The spark is asking which parts of a computation can run together and what the hardware changes about that answer. The next time I meet a similar problem, I would start by writing down the observable behavior, the constraints that define a correct result, and the smallest check that would distinguish a real fix from a plausible-looking change. For a design project, that means making requirements and drawings traceable. For a code contribution, it means connecting the issue, patch, review response, commit, and test output so a maintainer can follow the reasoning without reconstructing it from memory.

This is also why I keep the limits in the story. A portfolio entry is more credible when it identifies what was done, what the evidence confirms, and which environment or outcome still needs a fresh check. The public history is useful precisely because it lets a reader inspect those boundaries.
