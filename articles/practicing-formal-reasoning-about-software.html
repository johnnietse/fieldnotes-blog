This repository contains my solutions for Assignment 1 and Assignment 2 of the Software Specifications course at Queen's University. The assignments cover formal languages, automata theory, and algorithm verification.

📝 Assignment Details

Assignment 1

  • Topics: Regular languages, finite automata, NFA/DFA conversions.
  • Key Problems:
  • Problem 6: Email validator using a state machine.
  • Problem 7: DFA simulator for strings where the difference between a's and b's is ≤ 3.
  • Problem 8: Finite automaton (FA) simulator that checks if an input string is accepted by a given FA.

Assignment 2

  • Topics: Context-free grammars, PDAs, Turing machines.
  • Key Problem:
  • Problem 3: PDA simulator implementation.

def emailValidatorFSM_Finite_State_Machine(email: str) -> bool:

    # - The domain part (after '@') must contain only letters and at least one dot (.) separating the domain and top-level domain.
    # - The top-level domain must only contain letters.


    # initial state before processing anything
    state = "Start"

    def transition(char: str, current_state: str) -> str:
        # handle state transitions based on the current character
        nonlocal dot_in_domain

        # beginning of email (start local part)
        if current_state == "Start":

                return "local"
            return "invalid"

What I learned and what I would carry forward

Specification work shifts attention from a happy-path demo to the exact behaviors a program must guarantee.

The lasting lesson is specific to this record: The interest is how a precise statement of behavior can rule out whole classes of implementation mistakes. The next time I meet a similar problem, I would start by writing down the observable behavior, the constraints that define a correct result, and the smallest check that would distinguish a real fix from a plausible-looking change. For a design project, that means making requirements and drawings traceable. For a code contribution, it means connecting the issue, patch, review response, commit, and test output so a maintainer can follow the reasoning without reconstructing it from memory.

This is also why I keep the limits in the story. A portfolio entry is more credible when it identifies what was done, what the evidence confirms, and which environment or outcome still needs a fresh check. The public history is useful precisely because it lets a reader inspect those boundaries.
