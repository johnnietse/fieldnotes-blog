The spark

The interesting part is not only measuring a communication phase; it is being able to explain exactly which source, input, rank count, and binary produced a trace months later.

What makes this one hold my attention is that the motivating question has a concrete surface: A backup repository preserves modified Mantevo miniMD and miniFE sources, monitor scripts, Slurm-run traces, input files, build outputs, and the exact upstream patches needed to reconstruct the study.. That gives the work a way to be inspected. A reader can follow a requirement, trace its path into a file or drawing, and ask whether the artifact answers the original need. This is a more useful reason to care than the tool list by itself.

Why make a separate archive?

The README calls this a backup of a study run on Queen's CAC Frontenac between January and March 2026. It was copied from the cluster home directory on November 5 and checksum-verified with zero differing files. The README explicitly separates it from the public llm-d energy-routing project.

The archive keeps modified miniMD and miniFE sources, build outputs, run input, monitor traces, comparison JSON, upstream commit IDs, patches, and Git status files. A plot alone cannot explain which source, executable, input, and rank count produced a measurement.

The ignored files were part of the evidence

The first backup commit copied the study. A follow-up force-added 31 files that upstream .gitignore rules would otherwise omit. Generated files are often noise, but here they can be necessary to interpret the measurement.

The README identifies CAC Frontenac, a 32-rank miniMD run, executable miniMD_openmpi, input in.lj.miniMD, and January 21 result traces. It does not provide a complete compiler/module manifest for that run, so I do not invent one.

A good archive documents its exceptions

One miniMD/ref/chk symlink pointed to node-local Slurm scratch that no longer existed. Result filenames with colons were copied through WSL using U+F03A because Windows cannot represent colons; the README explains how to restore the names. The content is described as unchanged, but the filenames need conversion.

That turns a backup into a reconstruction recipe while leaving its limits visible: original artifacts remain on CAC, the old scratch target is gone, and filename restoration is a separate step.

Faithfulness

Every file is stored byte-for-byte (.gitattributes turns off line-ending conversion). The copy was checksum-verified against the cluster with rsync -c: 0 files differ. The originals also remain on the cluster in /global/home/hpc6081/, which CAC backs up.

One file that is not a copy

miniMD/ref/chk was a symbolic link to /lscratch/slurm-job-3121370-1/chk, the node-local scratch of an old Slurm job. That target no longer existed, so the link had no content; miniMD/ref/chk.symlink.txt records where it pointed.

File names containing ":"

Some result files on the cluster have : in their names (timestamps such as miniFE.32x32x32.P1.T1.2025-11-10-22:27:47.yaml). Windows does not allow : in file names, so the copy made through WSL stores each : as the private-use character U+F03A. Contents are unchanged; only that character in the name differs. To restore the original names, replace U+F03A with :.

Upstream .gitignore

The upstream folders' .gitignore files exclude build outputs and run results. In this backup all 31 such files were added anyway (git add -f), so every file from the cluster is here.

What I learned and what I would carry forward

The archive records a byte-for-byte checksum check with zero differences. The first backup commit was followed by a second that force-added 31 files ignored by upstream rules. The README also preserves a missing node-local scratch symlink and documents how WSL mapped colon characters in filenames for Windows. This is a reproducibility story with limits made visible instead of hidden.

The lasting lesson is specific to this record: The interesting part is not only measuring a communication phase; it is being able to explain exactly which source, input, rank count, and binary produced a trace months later. The next time I meet a similar problem, I would start by writing down the observable behavior, the constraints that define a correct result, and the smallest check that would distinguish a real fix from a plausible-looking change. For a design project, that means making requirements and drawings traceable. For a code contribution, it means connecting the issue, patch, review response, commit, and test output so a maintainer can follow the reasoning without reconstructing it from memory.

This is also why I keep the limits in the story. A portfolio entry is more credible when it identifies what was done, what the evidence confirms, and which environment or outcome still needs a fresh check. The public history is useful precisely because it lets a reader inspect those boundaries.
