pg_stat_statements LWLock Contention Reduction

Google Summer of Code 2026 proposal workspace: Improving PostgreSQL core stats tracking by partitioning the global LWLock bottleneck inside pg_stat_statements.c.

Build Dependencies

Required libraries for Ubuntu/WSL:

sudo apt-get install build-essential gcc make meson ninja-build libreadline-dev zlib1g-dev libssl-dev bison flex pkg-config perl libicu-dev

Compilation and Initial Setup

Cloning from the core mirror and building via Meson:

git clone --depth 1 https://github.com/postgres/postgres.git postgres-src
cd postgres-src
meson setup build --prefix=$HOME/pgsql
ninja -C build
ninja -C build install

Bootstrapping the test cluster:

$HOME/pgsql/bin/initdb -D $HOME/pgdata

Module Configuration

Load the runtime extension and restart the data node:

$HOME/pgsql/bin/pg_ctl start -D $HOME/pgdata -l $HOME/pgdata/logfile
$HOME/pgsql/bin/psql postgres -c "ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements';"
$HOME/pgsql/bin/pg_ctl restart -D $HOME/pgdata -m fast
$HOME/pgsql/bin/psql postgres -c "CREATE EXTENSION pg_stat_statements;"

Testing / Profiling Baseline

Generating pgbench mock workload to observe pgss_store hash eviction latencies:

$HOME/pgsql/bin/pgbench -i -s 1 postgres
$HOME/pgsql/bin/pgbench -c 10 -t 500 postgres

Monitor stats collection state:

SELECT query, calls FROM pg_stat_statements ORDER BY calls DESC LIMIT 5;

A small, real code sample

Excerpt from pg_stat_statements_prototype.c (line 8). Kept short enough to discuss; open the file for context.

 * a shared hashtable.  (We track only as many distinct queries as will fit
 * in the designated amount of shared memory.)
 *
 * Starting in Postgres 9.2, this module normalized query entries.  As of
 * Postgres 14, the normalization is done by the core if compute_query_id is
 * enabled, or optionally by third-party modules.
 *
 * To facilitate presenting entries to users, we create "representative" query
 * strings in which constants are replaced with parameter symbols ($n), to
 * make it clearer what a normalized entry can represent.  To save on shared
 * memory, and to avoid having to truncate oversized query strings, we store
 * these strings in a temporary external query-texts file.  Offsets into this
 * file are kept in shared memory.
 *
 * Note about locking issues: to create or delete an entry in the shared
 * hashtable, one must hold pgss->lock exclusively.  Modifying any field
 * in an entry except the counters requires the same.  To look up an entry,
 * one must hold the lock shared.  To read or update the counters within
 * an entry, one must hold the lock shared or exclusive (so the entry doesn't
 * disappear!) and also take the entry's mutex spinlock.
 * The shared state variable pgss->extent (the next free spot in the external
 * query-text file) should be accessed only while holding either the
 * pgss->mutex spinlock, or exclusive lock on pgss->lock.  We use the mutex to
 * allow reserving file space while holding only shared lock on pgss->lock.
 * Rewriting the entire external query-text file, eg for garbage collection,
 * requires holding pgss->lock exclusively; this allows individual entries
 * in the file to be read or written while holding only shared lock.
 *
 *
 * Copyright (c) 2008-2026, PostgreSQL Global Development Group
 *
 * IDENTIFICATION
 *	  contrib/pg_stat_statements/pg_stat_statements.c
 *
 *-------------------------------------------------------------------------
 */
#include "postgres.h"

#include <math.h>
#include <sys/stat.h>
#include <unistd.h>

What I learned and what I would carry forward

This is a proposal, not a merged PostgreSQL change. The strongest next step is to make the contention hypothesis measurable and compare it to the current implementation.

The lasting lesson is specific to this record: The spark is a systems bottleneck that appears when many queries compete to update shared statistics. The next time I meet a similar problem, I would start by writing down the observable behavior, the constraints that define a correct result, and the smallest check that would distinguish a real fix from a plausible-looking change. For a design project, that means making requirements and drawings traceable. For a code contribution, it means connecting the issue, patch, review response, commit, and test output so a maintainer can follow the reasoning without reconstructing it from memory.

This is also why I keep the limits in the story. A portfolio entry is more credible when it identifies what was done, what the evidence confirms, and which environment or outcome still needs a fresh check. The public history is useful precisely because it lets a reader inspect those boundaries.
