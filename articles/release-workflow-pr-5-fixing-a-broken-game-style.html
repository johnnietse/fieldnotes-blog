What I learned and what I would carry forward

The PR history shows a corrective change rather than an unrelated feature. That is the core lesson of the hotfix exercise.

The lasting lesson is specific to this record: A release can be correct in one area and still regress another, so the follow-up needs to be traceable to the release that introduced it. The next time I meet a similar problem, I would start by writing down the observable behavior, the constraints that define a correct result, and the smallest check that would distinguish a real fix from a plausible-looking change. For a design project, that means making requirements and drawings traceable. For a code contribution, it means connecting the issue, patch, review response, commit, and test output so a maintainer can follow the reasoning without reconstructing it from memory.

This is also why I keep the limits in the story. A portfolio entry is more credible when it identifies what was done, what the evidence confirms, and which environment or outcome still needs a fresh check. The public history is useful precisely because it lets a reader inspect those boundaries.
