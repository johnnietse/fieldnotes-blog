What I put in the issue description

The text below is my original public description, preserved so the scope and evidence are inspectable. It is useful context for reading later commits and review comments; it is not a substitute for the final merged code.

What happened:

When one of the EPP's servers fails to start, the EPP exits with status 1 and writes no error. In file-discovery mode the log ends right after EPP starting (file discovery mode) (plus some datalayer debug lines), with no error, panic or exit message, so the cause is invisible to the operator.

The error is dropped in two places, unchanged from v0.11.0 through v1.0.0 to current main:

  1. cmd/epp/main.go discards the error returned by Run:

https://github.com/llm-d/llm-d-router/blob/8f730719bfdd58b00e6ef39ee3b5f24b5fc8bfa9/cmd/epp/main.go#L45-L48

   if err := runner.NewRunner().
       Run(ctx); err != nil {
       return 1
   }
  1. In Run, the file-discovery branch returns runWithFileDiscovery's error without logging it (every other error on the setup path is logged with setupLog.Error first):

https://github.com/llm-d/llm-d-router/blob/8f730719bfdd58b00e6ef39ee3b5f24b5fc8bfa9/cmd/epp/runner/runner.go#L306 and runWithFileDiscovery ends with return g.Run(ctx) (L1413), where the run group returns the first runnable's error, wrapped with its name but not logged (cmd/epp/runner/rungroup.go L61).

So any error from the discovery, epp-server, health or metrics runnables (for example metrics server: listen tcp :NNNN: bind: address already in use) produces a silent exit 1.

How we hit it: we run the EPP in file-discovery mode on bare-metal Slurm nodes and restart it many times per job (one EPP start per measurement cell). We passed ports from a fixed range that happened to overlap the Linux ephemeral port range (net.ipv4.ip_local_port_range = 32768 60999, the default). Now and then an outgoing connection on the node (live or in TIME_WAIT) held one of the EPP's ports, the bind failed, and the EPP exited silently: 2 of about 1,150 EPP starts. It took a source read plus a local reproduction to find the cause, because the log never said what failed. Issue #2858 hit the same bind failure in TestRunWithFileDiscovery_Smoke (epp-server: gRPC server failed to listen - listen tcp :34575: bind: address already in use); the test saw the message only because it calls runWithFileDiscovery directly. #2861 fixed the test's port race but not the dropped error in the binary.

What you expected to happen:

The EPP logs the error before exiting, e.g. &quot;msg&quot;:&quot;EPP exited with error&quot;,&quot;error&quot;:&quot;metrics: metrics server: listen tcp :40004: bind: address already in use&quot;, so a failed start is diagnosable from the log alone.

How to reproduce it (as minimally and precisely as possible):

Hold the EPP's metrics port with an outgoing (client) socket, then start the EPP in file-discovery mode on that port (Linux):

# 1. something to connect to
python3 -c 'import socket; s=socket.socket(); s.bind(("127.0.0.1",40999)); s.listen(); s.accept(); input()' &
# 2. an outgoing connection whose LOCAL port is 40004
python3 -c 'import socket,time; c=socket.socket(); c.bind(("127.0.0.1",40004)); c.connect(("127.0.0.1",40999)); time.sleep(60)' &
sleep 1
# 3. the EPP with any working file-discovery config (e.g. the example in docs/discovery.md)
epp --config-file epp.yaml --pool-name epp --secure-serving=false --metrics-endpoint-auth=false \
    --grpc-port 40002 --grpc-health-port 40003 --metrics-port 40004 > epp.log 2>&1
echo "exit status $?"                                   # exit status 1
grep -ciE 'address already in use|bind' epp.log         # 0

The same happens when the port held is the gRPC port (40002) or the health port (40003). In each case: exit status 1, and no line in the log mentions the error. With all three ports free, the same command starts and serves normally.

We reproduced this with a binary built from v0.11.0 (our build also registers some out-of-tree plugins, but uses the same cmd/epp main/runner code). At current main (8f730719), cmd/epp/main.go and cmd/epp/runner/rungroup.go are byte-identical to v0.11.0, and the file-discovery path still ends in return g.Run(ctx), so the behavior should be the same on v1.0.0 and main.

Anything else we need to know?:

A possible fix, either of:

  • log in main before returning: e.g. ctrl.Log.Error(err, &quot;EPP exited with error&quot;) (or fmt.Fprintln(os.Stderr, err) if the logger may not be initialized yet), or
  • log in Run around the runWithFileDiscovery call, as the other setup errors already are.

Optionally, a docs note for file-discovery / bare-metal users: choose --grpc-port, --grpc-health-port and --metrics-port outside net.ipv4.ip_local_port_range, since a port there can be taken by any outgoing connection on the host. Moving our ports below 32768 is how we worked around it.

Environment:

  • Kubernetes version: none (file-discovery mode, no cluster)
  • llm-d-router version: v0.11.0 (cmd/epp built from source as a Go module dependency); code path verified unchanged on v1.0.0 and main at 8f730719
  • Cloud provider or hardware configuration: bare-metal Linux x86_64 GPU nodes under Slurm; EPP started next to vLLM servers and Envoy on the same node; reproduced on Linux x86_64 (WSL2) as well
  • Install tools: none (binary run directly)
  • Others: net.ipv4.ip_local_port_range = 32768 60999
